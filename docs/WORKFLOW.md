# Регламент работы с Claude Code

Кто что решает, как проверяется работа, как переходить между сессиями. Короткая версия — `../CLAUDE.md`, «Как работаем». Правила самого проекта (данные, сервер, код) — `../AGENTS.md`.

## 0. Шпаргалка владельца
1. **Задача — тремя пунктами:** что сделать, что не трогать, как проверить, что готово.
2. Долгая задача: `/goal <условие готовности>` — Claude работает, пока условие не выполнено.
3. После фичи: `/code-review high --fix` → проверка в браузере → коммит.
4. Крупное решение: `/council <тема>`.
5. Задача закончена или сессия разрослась (~200 тыс. токенов): `/handoff` → новая сессия с готовым промптом.
6. Effort: **medium** — обычная работа; **high** — корзина и цены, заявки, админка и вход, сервер, сложные баги; xhigh/max — разово, если не поддаётся.
7. Раз в месяц: `/doctor prompt-audit` — найти устаревшее в правилах.

## 1. Решения — сразу в файлы

Сессия может закончиться в любой момент, поэтому знание живёт только в файлах.

| Что | Куда |
|---|---|
| Решение владельца или Кирилла | Журнал `ROADMAP.md` §3 (новый раунд с датой и чьё решение) + сразу в нужные документы |
| Решение по дизайну | Ещё и `DESIGN.md` §11 «Правки» + правило в нужный раздел |
| Техническое решение Claude | `ROADMAP.md` §4: что решено и почему |
| Предложение, которое ждёт решения | `ROADMAP.md` §5 «Открытые вопросы» — с рекомендацией и сроком «нужно до» |
| Идея «на потом» | `FUTURE.md` |
| Итоги консилиума или проверки | `docs/_reviews/ГГГГ-ММ-ДД_тема.md` |
| Что сделано и проверено за сессию | `docs/sessions/ГГГГ-ММ-ДД.md` (AGENTS.md §7) |
| Текущий этап и что дальше | `CLAUDE.md`, «Текущий статус» — **не больше 4 строк**; подробности — в `ROADMAP.md` |

- Если решение принято, а в файлах его нет — решения не было.
- Журнал только дописывается. Решение меняется — новый раунд со ссылкой на прежний, в старой строке «→ раунд N».
- Решения Кирилла приходят через владельца: записываем «Кирилл (через владельца)».

## 2. Консилиум и проверка

### Консилиум (`/council <тема>`)
**Когда:** новый раздел сайта или крупная функция, изменение модели данных или формата контента, корзина и цены, авторизация, сервер и домен, спорный вопрос о продукте, пересмотр принятого решения.

1. Вход для экспертов — в файл `scratch/council_<тема>.md`: цели, ограничения, что оценить, пути к разделам документов. Прошлые выводы не передавать, если не нужна именно их проверка.
2. 3–4 независимых субагента с разными линзами (набор — в `.claude/skills/council/SKILL.md`). Друг друга не видят, файлы не правят, сначала своё мнение — потом сравнение с текущим планом.
3. Выжимки — в `docs/_reviews/`.
4. Владельцу: где согласны, где спорят, рекомендация. Пронумерованный список решений, на который можно ответить одной строкой («согласен со всем, кроме …»).
5. Решения — в файлы (§1), коммит.

**Мини-консилиум** для решений поменьше: 2 линзы. В работу идёт то, с чем согласны обе; спорное: техника — за Claude, бизнес — владельцу с рекомендацией.

### Проверка после изменений
Сначала **механические проверки** — бесплатно и за секунды: `npm run verify` (из `web/`), перед выкладкой `npx next build`. Агенты — только на то, что скриптом не проверить.

- **Волна 1:** 2 независимых проверяющих (только чтение, не видели, как делали работу):
  - `verifier-decisions` — соответствие решениям владельца и Кирилла и принципам `AGENTS.md` §1: ничего не потеряно, не выдумано (цены, отзывы, цифры), нет VIP, оплаты, ложной срочности;
  - `verifier-tech` — ошибки, краевые случаи, ловушки Next.js 16, данные и безопасность, простота.
- **Браузер — за основной сессией** (AGENTS.md §2): 375–390 и 1366 px, нет горизонтального скролла, корзина и заявка проходят, анимации проверять с отключённым скриптом. В отчёте — что именно обошли.
- **Находки разбирает основная сессия:** очевидное (ошибка, нарушение записанного правила) исправляет сразу; мини-консилиум — только по спорным. Голосований по каждой находке нет.
- **Волна 2** — только после серьёзных правок: 2 новых проверяющих, прошлых отчётов не видели.
- **Обычно 1–2 волны.** Третья — только по оставшимся ошибкам, а не новый полный аудит.

### Проверка кода
1. **Проверяющий ломает, а не только читает:** перед проверкой — коммит-снимок; `code-breaker` в своей рабочей копии (worktree) подкладывает ошибки в логику денег и корзины и пишет тест на `node --test`. Поимка засчитывается, только если на правильном коде тот же тест проходит. Полезные тесты переносит в проект основная сессия.
2. **Эталон — от другого автора:** для цен, скидок пакетов, выезда за МКАД и звука ожидаемое поведение пишет отдельный субагент только по `PRODUCT.md`, не читая код.
3. **Перед коммитом — `/code-review high --fix`** по всему диффу. Один проход; что не исправлено — в итог сессии с причиной.
4. Вход в админку и статистику, заявки (персональные данные клиентов), загрузки, сервер — ещё `/security-review`.

### Субагенты: когда да, когда нет
Делить работу **по контексту, а не по типу задачи**: субагент получает почти независимый кусок и возвращает короткий итог.
- **Да:** консилиум; независимая проверка («чёрный ящик»); поиск и чтение большого объёма; независимый кусок со своими папками (новая страница, раздел админки) — по правилам владения файлами из `AGENTS.md` §8.
- **Нет:** цепочки «пишет → дописывает → правит» — детали теряются на каждой передаче. Два пишущих агента в одних файлах. Свой `next dev`/`next build` у субагента, когда сервер уже запущен. Запись в базу из второго процесса.
- Важную проверку прогонять дважды или двумя проверяющими: поломка проявляется не в каждом прогоне.

### Модель и effort
- Основная сессия: Opus, **medium** по умолчанию; **high** — см. §0.
- Консилиум и проверяющие: Opus, high (заданы в `.claude/agents/`).
- Большие однотипные задачи (аудит всего проекта, правка сотен файлов): `ultracode:` в начале промпта, разово.

### Лимиты
Перед запуском нескольких агентов смотреть лимит в приложении; около 95 % пятичасового лимита новых не запускать. Раздутая сессия — повод для `/handoff`, а не для новых субагентов.

## 3. Вопросы и отчёты владельцу
- Всегда с рекомендацией и «почему».
- Идеи владельца — с конструктивной критикой, а не «согласен».
- Владельцу — вопросы о продукте, людях и деньгах, простыми словами. Технику решает Claude.
- После каждой партии изменений коротко: что изменилось и как посмотреть (ссылка или страница).

## 4. Одна задача — одна сессия
- Задача или этап — отдельная сессия; длинный этап — несколько сессий подряд.
- **Когда переходить:** задача закончена или контекст около 200 тыс. токенов (что раньше). Сессия больше 200 тыс., оставленная на час, сжимается сама и теряет детали.
- Перед переходом (`/handoff`): довести кусок до проверенного состояния → всё в файлы → запись в `docs/sessions/` → коммит → «Текущий статус» → промпт в `docs/_handoff/`. Предыдущий промпт — в `docs/_archive/handoff/`.
- **К следующему этапу — только по слову владельца.** Без него — промпт продолжения текущего этапа.
- Длинную сессию не делать «координатором»: каждый её ответ заново обрабатывает весь контекст.

### Шаблон промпта перехода
```text
Продолжаем проект «Улыбайся». Сначала прочитай CLAUDE.md, затем только документы, нужные для задачи.

Задача этой сессии: <что сделать — одним абзацем>.
Источники: <файлы и разделы с заданием>.
Уже решено и не пересматривается: <ключевые решения или раунды журнала ROADMAP.md §3>.
Не трогать: <что нельзя менять>.
Готово, когда: <npm run verify — 0 ошибок; браузер 390 и 1366 px; проверено verifier-decisions и verifier-tech; закоммичено; запись в docs/sessions/; «Текущий статус» обновлён>.
Бизнес-вопросы — задавай мне с рекомендацией; решения сразу записывай в файлы.
```

## 5. Git
- Репозиторий — корень проекта, копия в закрытом GitHub `Timohaostrovok2026/kira_sayt` (`origin`). Push в `main` — после проверенного коммита; `--force` и правка истории запрещены (хук).
- Коммит — на каждом законченном и проверенном шаге, сообщение понятное без контекста.
- Перед перестройкой файлов — коммит-снимок.
- Старые версии — в `docs/_archive/`, а не удалять.
- Выкладка на сервер не зависит от git: `web/scripts/deploy.sh` берёт рабочую папку. Выкладывать закоммиченное состояние.
